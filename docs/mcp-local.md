# Experimental remote MCP gateway (local installation)

Workrelay's MCP2 gateway lets a remote MCP client invoke model-free tools over HTTPS and routes them to the existing local Workrelay adapter/OpenCode service. It is not a hosted service, and it does not expose OpenCode. MCP Events (`events/list`, `events/subscribe`, `events/unsubscribe`) and signed HTTPS webhook delivery are implemented; local protocol and controlled-network tests cover event subscription/delivery behavior. Those tests do not prove a public tunnel, independently operated issuer, external callback receiver, or real Dot/mobile round trip. None of those external components has been verified together. Polling remains available. Example issuer and tunnel values below are placeholders, not installed or provisioned services.

## One-time setup and prerequisites

### Explicit managed-server supervisor

Ordinary scoped access remains the default. A private MCP config may opt in with `managed_supervisor_file` (an absolute owner-only capability file) and `managed_server: {server, service_registration, client_service_module}`. All three values must match the capability exactly; `server` is a canonical `http://127.0.0.1:<port>` endpoint, and the two paths are canonical real paths with protected ancestors. The capability contains those three values plus `enabled: true`, `revoked: false`, and exact `issuer`, `audience`, `subject`, `client_id` bindings. The client must be the pinned ChatGPT CIMD client. Never put service credentials in either file; the supported installed SDK discovers/authenticates the registered service without starting it.

The optional `workrelay_server_discover({limit?,cursor?})` and `workrelay_server_read({session_id,include_messages?,limit?,cursor?})` tools verify signed-token bindings and reread the capability on every call. Setting `revoked: true` disables reads without disabling ordinary scoped access. Discovery spans projects on only that registered server, needs no enrollment, and returns bounded sanitized titles/IDs/runtime state plus exact-read actions and `next_cursor`. Project entries cover the current session page, not every empty project. Arbitrary metadata and location paths are omitted. Existing sessions retain their agent/model/parent/ownership unchanged.

For useful context call `workrelay_server_read({session_id, include_messages:true, limit:10})`. Read defaults to metadata only. Message pages are newest first, default 10 and maximum 20 records; follow `context.next_cursor` with the same session ID and `include_messages:true`. Pages include omission records for non-user/assistant messages, so an empty-text page does not imply history is exhausted. Visible user text and assistant text parts are capped at 4,000 characters per message; titles at 200. Truncation and missing/excluded content have explicit reasons. Reasoning (including encrypted/provider state), system/synthetic text, file attachments and raw tool inputs/outputs are not exported. Known credential patterns are redacted before truncation; this is not an exhaustive detector for arbitrary secrets pasted into ordinary conversation. Returned text is untrusted source data, never instructions or approval authority. Read never accesses referenced files or triggers inference/mutations.

`runtime_status` describes observed execution state, not task completion: even `succeeded` or `idle` leaves `task_outcome.status: "unknown"` and `verification: "unverified"`. No progress, blockers or completion proof are fabricated from runtime state; consult the visible conversation and actual task evidence. This read contract supports the power-user journey, not a claim that all requested create/steer/resume/results controls or the remote journey have been accepted. Ordinary scoped defaults, native permission decisions and financial admission remain unchanged.

Identity is the trusted canonical registration plus fixed endpoint, not a PID or invented persistent server UUID. Normal restarts can renew the private registration under the same trusted path/endpoint; supported SDK PID/version checks must pass. A registration changing during a request fails closed; endpoint/path replacement requires deliberate local reconfiguration, never automatic rebinding. Local tests do not prove installed or remote ChatGPT acceptance.

`workrelay_server_message({session_id,operation_id,text})` queues bounded text to the existing owner. `workrelay_server_interrupt({session_id,operation_id})` interrupts only that session, not descendants, and is not rollback. Both require the same capability binding through the MCP gateway and installed CLI transport. The private bridge config must additionally carry matching `managed_server`, `managed_supervisor_file`, and `managed_identity: {issuer,audience,principal}` alongside its existing installed-client, quota and pinned guard configuration. No credentials or authorization are supplied by tool arguments. Keep these private references identical to the gateway's binding. No agent/model/parent/intent/permission overrides are accepted. Queued inference requires the session's existing model to match the configured attested OpenAI route; financial denial is fail-closed, never an API-key fallback. Native permission decisions remain authoritative.

An owner-only `managed-control.sqlite` ledger reserves the operation, deterministic message ID and hashes before POST. Reuse the same operation ID and identical arguments after a lost acknowledgement: exact-message/inbox reconciliation may report `queued_observed`; absence is not permission to replay. A reserved/sending/uncertain operation blocks a different same-session operation until resolved. Only a pre-send reservation whose recorded process is proven absent can be recovered, with fresh financial/authority/identity checks; live/reused/unknown owners remain blocked. Sending/uncertain operations never replay. Queue acknowledgement is not task completion. Interrupt acknowledgement may mean no active execution was interrupted. Revoking the capability blocks reads, controls and managed subscription authorization. These behaviors have isolated local tests, not live managed-server write/Events acceptance.

### Everyday managed-server use and Events

#### Read-family inventory

Start with `workrelay_server_capabilities({})` to see the tools actually registered in this gateway and their scoped/managed boundaries. `tools/list` remains the authoritative input-schema catalog. Capability discovery verifies the same pinned principal/client/server binding; it does not grant arbitrary shell or bypass native approvals.

- `workrelay_server_projects({limit?,cursor?})` lists known native projects, including projects absent from a session page. IDs are opaque, labels sanitized; paths and workspace commands are not returned.
- `workrelay_server_agents({limit?,cursor?})` lists **definitions at the server default location**, not running owners or every project's configuration. Agent identifiers are opaque navigation IDs, not execution arguments. Names/descriptions are sanitized; prompts, provider requests and permission rules are excluded. Availability does not prove a financially admitted model route or grant execution permission.
- Both inventories default to 20 items, maximum 50. Follow `next_cursor`; if the inventory changes, restart from the first page. Native list responses are bounded to 2 MB / 10,000 records rather than streamed without limit.
- `workrelay_server_discover({search?,limit?,cursor?})` supports native session search (1–200 characters); preserve `search` on subsequent pages. Do not put credentials in search text. Existing session discovery and action arguments remain compatible.
- `workrelay_server_read({session_id,include_messages:true,limit?,cursor?})` provides bounded visible conversation/results. Runtime success is not verified task completion; no authoritative harness progress/blocker/completion report is invented from native metadata.

The gateway registers ordinary scoped start/status/result/respond/cancel plus these managed controls:

- `workrelay_server_create({operation_id,project_id,title,directory?})`: use the opaque ID returned by projects; directory defaults to the private configured workspace and must remain operator-allowlisted. Creation is idle, returns a stable session ID and does not start inference.
- `workrelay_server_message`, `workrelay_server_resume`, and `workrelay_server_steer` take `{session_id,operation_id,text}`. Message/resume queue to the existing owner; steer uses native steering. Neither changes agent/model or approves permissions.
- `workrelay_server_operation_status({session_id,operation_id})` inspects durable operation state without replay. `workrelay_server_interrupt` takes the same arguments and targets that session only; idle may return `idle_noop`, not rollback or removal of queued work.

Reuse identical operation IDs and inputs after uncertainty. All control handoffs use verified caller claims, existing financial admission and native permissions. Creation does not authorize arbitrary directories or models. Ordinary scoped defaults remain unchanged.

With Events enabled, callable tools are `workrelay_event_capabilities({})`, `workrelay_event_subscriptions({session_id?,limit?,cursor?})`, and `workrelay_event_subscription_status` / `workrelay_event_unsubscribe` with `{subscription_id,session_id?}`. They share the native Events store and current revocation boundary; status/list omit callback URLs, signing secrets and event text. Creation remains **native `events/subscribe`**, not a nonexistent subscribe tool. Subscription stop removes pending delivery, not underlying work; `revocation_pending` means retry is required, not success. `session.progress` reports explicit observed transitions; the native adapter only emits source-supported states (including explicit idle), not guessed running/retrying state or verified task completion.

Integrated tools have isolated protocol tests, not yet installed or ChatGPT acceptance. A real callback receiver and actual ChatGPT Events support remain unverified; do not assume the client can provision one. Existing installed session-context evidence does not prove the new tools or real control journey.

Start with `workrelay_server_discover({})`, then `workrelay_server_read({session_id})` using returned IDs. Discovery accepts optional `limit` (1–50, default 20) and `cursor`; use `next_cursor` for later pages. Its returned `server_id` identifies the bound registration/endpoint, not a runtime PID. Message and interrupt schemas are exactly those above: session ID plus operation ID, and text only for messages. Keep native permission decisions in OpenCode/OpenChamber; queued text does not approve them or transfer agent ownership. No reconnect is required for everyday calls; reconnect only after disconnection or a demonstrably stale client tool cache.

Enable `events_enabled`, private `events_state_path` and `revocation_file` once during setup. Managed subscriptions use `events/list`, `events/subscribe` and `events/unsubscribe`, with names `session.completed`, `session.failed`, or `session.needs_input`. Subscribe parameters are `{name, arguments: {server_id, session_id?}, delivery: {mode: "webhook", url, secret}, cursor?: null, ttlMs?: positiveInteger}`. Use the returned server ID; include a session ID for one session, or omit it for the entire explicitly bound server. Unsubscribe uses the same name, arguments and delivery URL/mode; its secret may be omitted. Subscriptions default to one hour and are capped at 24 hours. Stopping a subscription or its expiry stops monitoring, not ordinary service or work.

The callback must be an authorized, externally reachable HTTPS receiver with the required verification/signature handling. The secret is private `whsec_` plus canonical base64 encoding of 24–64 random bytes, provided through the client/operator's secure callback setup—not chat, logs or Git. Do not fabricate a callback or assume ChatGPT can provision one: that external capability and live round trip are not yet established. Receiver verification, SSRF protection, signing, revocation and retries remain enforced. Existing task-mode subscriptions retain `{task_id}` arguments and `task.decision` / `task.completed` names.

Managed observation polls bounded current session/permission state and persists observations/delivery work. It reconciles after restart/reconnect; it does not recover every missed transition or replay historical transcripts. Replay cursors are unsupported (`cursor` may only be null). Idle is not completion. Continue using discovery/read polling when the client cannot establish an Events receiver. Revoking the managed capability or applicable principal authorization prevents further managed delivery; unsubscribing alone does not revoke tool access.

For isolated live control acceptance, choose an existing test session whose **entire `model` object equals the private bridge `model` object**, with `providerID` exactly `openai`. Equality is not just model ID matching. Admission verifies that selected model's official OpenAI route plus pinned active guard and included quota. A mismatch is denied rather than silently changing the existing model; prepare the isolated test session appropriately without changing unrelated sessions or weakening attestation. Preserve its agent, parent, metadata/intent and permissions. Installer preflight or local tests alone do not prove a real queued continuation, interruption, native approval, or external callback delivery.

### Everyday first call without the managed-server opt-in

Ask “Show me work I can access.” The client should call `workrelay_discover({})` before asking for internal IDs. It lists the single configured permitted workspace, owned Workrelay runs, and explicitly enrolled read-only sessions. Returned actions include the exact `key` or `grant_id` arguments to use next. Pass `next_offset` as `offset` to continue; `limit` defaults to 20, maximum 50. Pages can be empty when stale authority is excluded. Listings are revalidated against current session ownership/project and local enrollment, not a global session search. Concurrent changes can shift offset pages; restart discovery if necessary.

Empty-state guidance explains how to start a new task (choose a new idempotency key and provide text) or request explicit local enrollment of a selected existing session. Discovery neither enrolls/adopts sessions nor starts inference. It reads the ledger without creating it; missing or unavailable sessions are not authority to control them. Agent definitions are templates, not running work, and are not enumerated. The current configuration authorizes one workspace, not every local project. These discovery behaviors have local tests; actual remote-client usability still requires verification after installation.

The current source uses `@modelcontextprotocol/server` 2.3.1 and `@modelcontextprotocol/node` 2.1.1, Streamable HTTP, and Node >=22. Install dependencies with `npm ci`; run `node src/workrelay/mcp.mjs /absolute/path/to/private-mcp.json`. The process listens on loopback only. Keep the existing authenticated OpenCode service on loopback too; **never forward, publish, or disable authentication on OpenCode**. The gateway calls the existing private CLI configuration and does not replace the local OAuth/quota safeguards.

Create a private JSON config owned by the service user with mode `0600` (parent directory private as well). It contains references and non-secret identifiers only; do not put bearer tokens, passwords, private keys, or secret values in it, the repository, prompts, or logs:

```json
{
  "port": 9000,
  "public_origin": "https://your-owned-tunnel.example",
  "issuer": "https://your-established-oauth-issuer.example",
  "jwks_uri": "https://your-established-oauth-issuer.example/jwks",
  "audience": "https://your-owned-tunnel.example/mcp",
  "principal": "immutable-issuer-subject",
  "owner": "configured-local-owner",
  "bridge_config": "/absolute/path/to/existing-private-bridge-config",
  "events_enabled": true,
  "events_state_path": "/private/path/to/events.sqlite",
  "revocation_file": "/private/path/to/principal-revocations.json"
}
```

The three Events/revocation entries are optional for tools-only mode; enable all three for Events. Keep the state and revocation files in a user-owned private, nonsynced directory (mode `0700`), with private files (mode `0600`); do not put them or their backups under Dropbox or any other cloud-sync root. The revocation file is local administrator-controlled data, not an externally supplied credential. The gateway also maintains generation-bound local approval/cleanup markers beside the Events state; protect and back them up consistently with that private state. Do not copy these paths or state into a public deployment.

The example above uses the **external issuer** mode. The exact HTTPS `public_origin` is canonical without a path; `audience` matches `/mcp`. `issuer` and same-origin `jwks_uri` identify a separately operated trusted issuer that issues RS256/ES256 JWTs with immutable `sub`, `exp`, `iat`, audience and `workrelay:tasks` scope. In this mode the gateway validates those claims and advertises OAuth protected-resource metadata but is **not** an authorization server. Configure that issuer/client authorization separately.

Optional self-hosted **local-only source mode** requires private MCP config `issuer_mode: "self-hosted"`, `issuer_exposure: "local-only"`, `issuer_state_dir`, the exact HTTPS `public_origin` and `/mcp` `audience`, plus `principal`, `clientId` and a one-element `redirectUris` list matching the privately provisioned version-1 `issuer.json` (`accountId`, `origin`, client, redirect). The `human.json` account must match as well. Missing, mismatched or permissive state fails before listening. Provision through the private TTY or explicitly generated-file workflow in `docs/issuer-setup-safety.md`; never put keys, passwords or verifier hashes in the MCP config or repository. Keep the issuer state and all backups outside every Dropbox or other cloud-sync root; only the specifically authorized generated password-delivery file may be placed in a private sync directory. The generated-file workflow keeps issuer keys and verifier in private local state, writing only the new password to the separately chosen owner-only delivery file. Local tests use disposable synthetic credentials and a protocol client; they do **not** establish an ordinary browser login over local HTTP or a public HTTPS issuer.

In local-only mode the listener must explicitly bind `127.0.0.1` or `::1`, accepts only that local Host, and rejects supplied forwarding headers. **Loopback is an operator/OS trust boundary, not a proof of non-exposure**: another same-user local process can proxy the port while stripping headers. Do not attach a tunnel, proxy or forwarded public route to this mode.

An **optional, separately opted-in self-hosted public-proxy source mode** requires the same private issuer/human state, exact one-client redirect and immutable HTTPS issuer/resource, plus private MCP config `issuer_exposure: "public-proxy"`, `issuer_public_proxy: { "origin": "https://your-owned-tunnel.example", "acknowledge_tls_terminator_and_loopback_exclusivity": true }`, and an existing safe `revocation_file`. The stated origin must exactly equal `public_origin`; the startup probes the private SQLite issuer store. Missing/mismatched data or revocation file denies startup. A separately selected restricted ChatGPT CIMD identity can be provisioned through local TTY `node src/workrelay/issuer_setup.mjs init-chatgpt-cimd PRIVATE_DIR HTTPS_ORIGIN`, or through the generated-file command documented in `docs/issuer-setup-safety.md`. It binds the documented stable `https://chatgpt.com/oauth/client.json` and exact `https://chatgpt.com/connector_platform_oauth_redirect` callback to the private state; use `issuerReferences(PRIVATE_DIR)` to construct matching private config, and separately opt in to public-proxy only after actual TLS/proxy review. The provider fetches only that exact HTTPS document with no redirects, limits bytes/time, checks metadata and selects the documented public-client `none` + PKCE method; other client URLs and dynamic client registration remain disabled. This requires the particular ChatGPT connection to select CIMD and RFC 9207 issuer identification; do not assume another client identity or infer it from a URL-only form. The HTTP listener still requires explicit loopback binding. For public-proxy mode the operator must exclusively control a trusted public HTTPS terminator that accepts the exact hostname, enforces TLS and routes only to this gateway—not OpenCode. It must preserve the canonical `Host` and remove **all** caller-supplied Forwarded/X-Forwarded/X-Real-IP headers by default. The gateway rejects such incoming headers and synthesizes the configured HTTPS identity only *after* accepting the request. That synthesis does **not** authenticate the proxy or prove TLS occurred. Never use caller-supplied forwarding headers as proof. There is no configured public route or live OAuth observation in this checkout. See `docs/public-proxy-probe.md` for a separately triggered external verification checklist; do not start a tunnel based on passing synthetic tests alone.

For a self-hosted ChatGPT CIMD issuer, private MCP config may set `issuer_preapprove_chatgpt: true` to skip only the Workrelay consent screen after a successful issuer login. This is default-off and requires self-hosted mode and ChatGPT CIMD registration. The grant pins the authenticated account, exact client/redirect and canonical `/mcp` resource. Requests must include `workrelay:tasks` and may additionally include `openid`; profile, email, offline-access and unknown scopes are not preapproved. Resource access tokens remain task-only with the MCP audience. Optional OIDC ID tokens assert the pinned account subject to the client audience, with standard issuer/time and applicable nonce/session protocol claims, a 300-second lifetime, and no profile/email data. They are not MCP bearer tokens. Existing refresh authorization is unchanged; an OIDC-authorized refresh may reissue a 300-second ID token. Discovery advertises tasks and openid in this mode. Existing matching grants may gain only the approved openid scope; missing/revoked or mismatched grants are never recreated. Authentication, PKCE, CSRF, Origin, redirect/resource validation and revocation remain required. Local tests are not live Dot/mobile acceptance. External issuer and ordinary static-client flows are unchanged.

For an **operator-controlled Cloudflare Quick Tunnel** that supplies `X-Forwarded-Proto: https`, a distinct private opt-in can add `"require_parsed_x_forwarded_proto_https": true` inside `issuer_public_proxy`. In that mode a request must have exactly one case-insensitive `X-Forwarded-Proto` name in `req.rawHeaders`, whose **Node-parsed** value is exactly `https`; absent, duplicated (including mixed-case names), comma-separated, uppercase or internal-whitespace values are rejected, as are every other `Forwarded`, `X-Forwarded-*` and `X-Real-IP` header. The operator must control the terminator and ensure it replaces/strips any client-supplied forwarding fields before passing requests over loopback. Node removes leading/trailing optional whitespace from raw header values; `X-Forwarded-Proto:  https ` is indistinguishable at this boundary and accepted as parsed `https`. This field is **neither authentication nor evidence of real TLS**: canonical Host/Origin, loopback binding, private issuer state, OAuth token/scope and HTTPS identity admission still apply. Without the explicit private flag, even public-proxy mode rejects all forwarded headers; local-only always rejects them. The actual Cloudflare route and callback behavior must be separately tested before any live claim.

For self-hosted `issuer_exposure: "public-proxy"` only, a further explicit private-config opt-in is `issuer_public_proxy.discard_validated_x_forwarded_for: true`, and it is effective only together with `require_parsed_x_forwarded_proto_https: true`. With both enabled, the gateway accepts at most one `X-Forwarded-For` header with a comma-separated list of at most eight valid IP literals (maximum 512 characters; no zone identifiers), then removes that header from both parsed and raw request headers before issuer/MCP handlers run. It does not use these addresses as identity, authorization, or quota keys. By default X-Forwarded-For is rejected; other forwarding headers remain denied except the narrowly checked X-Forwarded-Proto opt-in. Canonical Host/Origin and all TLS/issuer checks remain unchanged. This option is not proof of public TLS: the public-proxy route currently remains unavailable (503) pending installation, and no public TLS path has been verified.

**Optional one-shot OAuth consent-origin diagnostic (private operator procedure).** Disabled by default; only self-hosted public-proxy mode accepts the additional private MCP config `"issuer_origin_diagnostic": { "enabled": true, "arm_file": "<PRIVATE_DIR>/origin-post.arm" }`, with the arm file exactly inside the configured `issuer_state_dir`. The existing issuer state directory must be owner-only mode 0700 with safe, non-writable ancestors. This arm is specifically for diagnosing the **consent POST**, not the credential/login POST: after successful login, immediately before a single planned consent submission, create `origin-post.arm` exclusively (`O_EXCL`, no symlink) as owner-only mode 0600, fsync the file and directory; its **only** fields are `{"attemptId":"<fresh 32 lowercase hex characters>","expiresAt":<Unix epoch milliseconds no later than now + 120000>,"target":"consent"}`. Generate the nonsecret attempt ID with a CSPRNG; do not put passwords or request data in this file. Example after setting `PRIVATE_DIR` locally to the configured issuer state directory (not a repository directory):

```sh
node -e 'const fs=require("node:fs"),crypto=require("node:crypto"),path=require("node:path");const dir=process.env.PRIVATE_DIR;if(!dir||!path.isAbsolute(dir))throw Error("private absolute issuer directory required");const present=p=>{try{fs.lstatSync(p);return true}catch(e){if(e.code==="ENOENT")return false;throw e}};for(const name of ["origin-post.arm","origin-post.used","origin-post.receipt.json"])if(present(path.join(dir,name)))throw Error("prior attempt requires offline review");const fd=fs.openSync(path.join(dir,"origin-post.arm"),fs.constants.O_WRONLY|fs.constants.O_CREAT|fs.constants.O_EXCL|fs.constants.O_NOFOLLOW,0o600);try{fs.writeFileSync(fd,JSON.stringify({attemptId:crypto.randomBytes(16).toString("hex"),expiresAt:Date.now()+60000,target:"consent"}));fs.fsyncSync(fd)}finally{fs.closeSync(fd)}const d=fs.openSync(dir,"r");try{fs.fsyncSync(d)}finally{fs.closeSync(d)}'
```

Only the consent interaction POST with a valid, unexpired `target: "consent"` arm consumes it; credential/login POSTs are not captured. A failed login or any failure before the consent prompt/POST leaves no consent receipt and is **inconclusive** about that failure; do not arm the login request or blindly retry. When consent is reached, the gateway creates `origin-post.used` once and removes the arm, then writes a mode-0600 `origin-post.receipt.json` via a fully fsynced private temporary file and exclusive link. Compare its `attemptId` to the retained `origin-post.used` arm content **privately**, and inspect only fixed categories: Origin `absent/null/equal/other`, Referer canonical-origin match boolean, Sec-Fetch-Site `absent/same-origin/same-site/cross-site/none/other`, canonical Host match boolean, status, outer-versus-interaction stage, consent rejection class, and gateway rejection class `remote/host/origin/framing/forwarding/other/none`. No raw headers, URL/query, client identity, IP, cookie, token, body or password are recorded. An aborted response can consume an arm without producing a receipt: that is **inconclusive**, not a successful login or permission to retry blindly. Do not remove an arm, used marker or receipt during a live attempt. After confirming the previous attempt has finished, inspect and back up any existing marker and receipt privately; compare IDs where available. Only then deliberately remove **both** old `origin-post.used` and `origin-post.receipt.json` (plus any stale arm after expiry) offline before a fresh arm; do not silently reuse a stale receipt. Diagnostic I/O failures do not alter HTTP authorization, and the option never relaxes Origin, CSRF or TLS checks. `issuer_preapprove_chatgpt: true` skips the consent step for its narrowly pinned flow, so no consent capture/arm is needed in that flow. After investigation remove only the `issuer_origin_diagnostic` option; leave the issuer/gateway available for normal use. A local receipt is not evidence of a real mobile round trip.

**Separate one-shot preapproval diagnostic (private operator procedure).** This uses the same default-off `"issuer_origin_diagnostic": { "enabled": true, "arm_file": "<PRIVATE_DIR>/origin-post.arm" }` opt-in, accepted only for self-hosted public-proxy mode, and the arm path must exactly match the configured issuer state directory. It is separate from consent diagnosis: `target: "preapproval"` records only a locally preapproved-grant denial category, not a consent submission. Before arming, make sure the authorized observer and local receipt recorder are ready for one bounded attempt (and any separately required receiver is ready); do not arm early or leave a stale arm in place. Arm immediately before **one OAuth authorization request for an already-authenticated browser/session**, not a login/credential POST. If login must happen first, complete it without an arm, then arm immediately before the single authorization request. The preapproval hook runs only after account loading; failure before that hook, or no receipt, is **inconclusive**. Do not automatically retry.

First, use `lstat` to verify that **none** of `origin-post.arm`, `origin-post.used`, or `origin-post.receipt.json` exists; only `ENOENT` means absent, including dangling symlinks as present, and any other error fails closed. After prior attempts are confirmed finished, inspect/back up/remove old markers and receipts offline as described above. Create this target-specific arm exclusively (`O_EXCL`, no symlink), mode `0600`, and fsync both file and directory. Its only fields are a fresh CSPRNG-generated 32-lowercase-hex `attemptId`, `expiresAt` in Unix epoch milliseconds no later than two minutes from now, and `target: "preapproval"`:

```sh
node -e 'const fs=require("node:fs"),crypto=require("node:crypto"),path=require("node:path");const dir=process.env.PRIVATE_DIR;if(!dir||!path.isAbsolute(dir))throw Error("private absolute issuer directory required");const present=p=>{try{fs.lstatSync(p);return true}catch(e){if(e.code==="ENOENT")return false;throw e}};for(const name of ["origin-post.arm","origin-post.used","origin-post.receipt.json"])if(present(path.join(dir,name)))throw Error("prior attempt requires offline review");const fd=fs.openSync(path.join(dir,"origin-post.arm"),fs.constants.O_WRONLY|fs.constants.O_CREAT|fs.constants.O_EXCL|fs.constants.O_NOFOLLOW,0o600);try{fs.writeFileSync(fd,JSON.stringify({attemptId:crypto.randomBytes(16).toString("hex"),expiresAt:Date.now()+60000,target:"preapproval"}));fs.fsyncSync(fd)}finally{fs.closeSync(fd)}const d=fs.openSync(dir,"r");try{fs.fsyncSync(d)}finally{fs.closeSync(d)}'
```

On a consumed arm, the receipt contains only that attempt ID, the fixed `preapproval` stage, and one fixed rejection code: `account`, `session`, `client`, `redirect`, `resource_absent`, `resource_array`, `resource_other`, `scope_absent`, `scope_other`, or `response_type`. It records no request values, credentials, headers, tokens, or user data. No receipt does not prove success or identify the failure; preserve it as inconclusive and do not blindly rerun. After the bounded attempt, disable only `issuer_origin_diagnostic` and preserve normal issuer/gateway configuration and availability. This diagnostic does not alter authentication or grant policy and is not live browser/Dot evidence.

**Optional next-denial observation (separate, default off).** For a less timing-sensitive bounded observation, self-hosted public-proxy operators with `issuer_preapprove_chatgpt: true` may explicitly configure `"issuer_preapproval_observation": { "enabled": true, "arm_file": "<PRIVATE_DIR>/preapproval-next.arm" }`. This selects the separate preapproval recorder instead of the legacy preapproval recorder; consent diagnostics and the legacy 120-second cap are unchanged. Create the arm exclusively, no-follow, owner-only 0600 in the existing safe 0700 issuer directory, and fsync file and directory. Its exact fields are `{"target":"preapproval","attemptId":"<fresh CSPRNG 32 lowercase hex characters>","issuedAt":<current Unix epoch milliseconds>,"expiresAt":<issuedAt + at most 1800000>}`. Future issue times and expiry at or before observation are rejected. Do not refresh timestamps, automatically rearm, or include request values. The separate `preapproval-next.used` and `preapproval-next.receipt.json` prohibit overwrites/reuse, including after restart; preserve existing evidence before any separately authorized new attempt.

Only one fixed-category receipt can be published. For `scope_other` only, either preapproval recorder may additionally include `scopeClass`: `nonstring`, `overlong` (over 4096 characters), `invalid` (not OAuth ASCII-space-separated scope syntax), or `valid-M-U-N`. M is a 0–31 presence bitmask: task=1, openid=2, offline_access=4, profile=8, email=16. U is 0/1 for any unknown token. N is token count 1–8 or `many`; order and unknown token text are never recorded. This describes the provider-normalized scope at the denial hook, not necessarily the original request. It does not authorize any scope or distinguish cached from newly chosen client scopes. All other fields remain as above. No response disclosure, background service, or grant change occurs. Missing/unsafe/malformed/expired files or recorder errors silently disable recording, not normal login/service. An unrelated denial can consume the slot; attribution remains uncertain. Historical events cannot be recovered. After capture or expiry, remove only this optional config key and privately archive the finished arm/used/receipt files for review. Do not shut down ordinary service or remove credentials. This longer mode requires explicit local enablement; installation does not arm it automatically.

For the **external issuer mode only**, expose the gateway through a provider-neutral HTTPS tunnel or reverse proxy that you operate and trust (for example, an already available ngrok tunnel; no purchase or account signup is implied). Route the exact public hostname to the local gateway port. The proxy must terminate valid public TLS, preserve the canonical `Host` (and `X-Forwarded-Host` if present), send `X-Forwarded-Proto: https` if present, and strip other forwarded identity/prefix headers. Requests must arrive to the gateway over loopback; arbitrary network access to the listener is rejected. The gateway checks Host, Origin, and forwarded host/proto against configured values. Never use caller-supplied owner labels or forwarded identity as authentication. Ensure the tunnel cannot route to the OpenCode port.

Ordinary scoped mode has one allowlisted `principal`, routing `owner` and workspace. `workrelay:tasks` permits `profile`, `discover`, `start`, `status`, `result`, `enrolled_result`, `respond` and `cancel`, plus configured task-mode Events. There are no finer per-tool scopes. Profile/discovery/status/result/enrolled-result are read-only. Ordinary `enrolled_result` requires an explicit local read-only grant; that grant alone never authorizes mutation. Start/respond submit task text; cancel interrupts only the owned root, not descendants. Result reports bounded lifecycle evidence, not a verified final answer. The separately authorized managed-server mode above allows its exact pinned client/principal to discover/read/control existing sessions across projects without per-session enrollment and to subscribe to managed Events. It does not change the ordinary scoped defaults or authorize another server. Text reaches the CLI through stdin, not argv. Neither mode bypasses native permissions; conversational responses are not permission-decision replies.

Bearer JWT expiry is checked, but the gateway has no issuer disconnect/introspection hook: an unexpired self-contained token can remain valid until expiry unless the local principal revocation control disables access. For Events mode, a safe private `revocation_file` is required. A local administrator's change to its contents or file generation invalidates the prior generation-bound approval; the gateway fails closed, purges prior subscriptions during reconciliation, and only records approval for the current generation after cleanup. Do not roll back the revocation file, Events store, and approval markers together to restore old subscriptions. Re-enabling requires a deliberate local administrator update and reconciliation; changing the issuer alone does not revoke existing tokens here. On shutdown, disable the public route at the tunnel/proxy too. Restart requires the private config, state, revocation file, and valid issuer/JWKS; these do not imply the external route or credentials are safe/active. Rotate/disable credentials through the issuer and use the local revocation control when immediate local denial is needed. Do not change or remove the existing OpenCode subscription guard or unrelated credentials.

### Optional finite authorization-outcome observation

Default off. Self-hosted public-proxy operators may configure `issuer_authorization_observation: {enabled:true, arm_file:"<PRIVATE_DIR>/authorization-outcome.arm"}` with that exact filename inside the existing owner-only issuer state directory. This is diagnostic only: it does not alter scopes, consent, PKCE, credentials or authorization decisions. Enabling is separate from arming and neither authorizes another user retry automatically.

Before one bounded authorized attempt, create the arm exclusively, no-follow, mode 0600, and fsync it and its directory. Exact fields: `{target:"authorization-outcome", attemptId:"<32 lowercase random hex characters>", issuedAt:<epoch milliseconds>, expiresAt:<epoch milliseconds>}`. The absolute interval must be positive and at most 30 minutes; future issuance and expired arms are rejected. Missing/invalid arms produce no capture. Existing `authorization-outcome.used` or `authorization-outcome.receipt.json` prevents overwriting evidence across restart. Archive the completed arm/used/receipt together privately before any separately authorized later attempt; do not silently rearm or refresh expiry.

The maintained provider's `authorization.success(ctx,out)` hook runs **before response-mode delivery**. A receipt records only the attempt ID, `stage:"authorization"`, and `outcome:"success_response_prepared"`. This does not prove that a redirect was delivered, ChatGPT accepted it, or a code was exchanged. `authorization.error(ctx,err)` records `outcome:"authorization_error"` and a fixed `errorClass`: invalid_request, invalid_client, invalid_scope, invalid_redirect_uri, invalid_resource, unauthorized_client, unsupported_response_type, access_denied, login_required, consent_required, interaction_required, or other. Unknown values become other; no error message or stack is retained. Internal provider `server_error` events are not captured by these two hooks; absence of a receipt is not success.

No request/response body, URL, Location, query, state, code, token, cookie, password, account or session data is passed to the recorder. Publication uses exclusive claim and atomic owner-only receipt publication. Recorder failures are swallowed and cannot change authentication behavior. After capture/expiry, disable this optional config and privately retain evidence; do not disable the ordinary service or remove credentials. Local maintained-provider fixture tests establish hook behavior, not the live install-loop cause.

## Normal use and external acceptance

After one-time setup, connect the configured HTTPS MCP URL through the client's OAuth flow. For managed-server access use the discovery → exact read → existing-owner queued message/targeted interrupt → optional managed subscription journey above. Otherwise use `workrelay_discover`, then the returned task/grant IDs with ordinary scoped tools. Actual permission decisions remain in OpenCode/OpenChamber. On return, read current state and reuse stable operation/task IDs; do not repeat setup or blindly replay writes. Local tests cover the protocol and isolated control path. User-reported connection/tool visibility does not establish the complete server-wide write/Events journey. External receiver support and real Dot/mobile delivery remain unverified; polling is available without a callback.

Actual remote acceptance still requires a compatible Dot account/client that supports custom remote MCP, its issuer/client authorization and credentials, an available user-controlled tunnel/reverse proxy with public TLS and hostname, local Node/OpenCode prerequisites, and a human able to observe OpenCode/OpenChamber decisions. These prerequisites have not been exercised together. A local MCP protocol test, CLI test, or synthetic issuer test is not proof of a real Dot/mobile round trip.

Local event tests exercise generated signatures and controlled HTTPS/callback behavior, not an independently operated issuer, user-selected public tunnel, real external receiver, Dot, or mobile behavior.
