# Experimental remote MCP gateway (local installation)

Workrelay's MCP2 gateway lets a remote MCP client invoke model-free tools over HTTPS and routes them to the existing local Workrelay adapter/OpenCode service. It is not a hosted service, and it does not expose OpenCode. MCP Events (`events/list`, `events/subscribe`, `events/unsubscribe`) and signed HTTPS webhook delivery are implemented. Controlled live probes verified native permission-ask → `session.needs_input` signed HTTPS acknowledgement and a separate financially guarded existing-session continuation → fresh-generation completion acknowledgement, with protected identity unchanged. The ask gate survived unsubscribe and was cleared only by reject cleanup; no stale completion was observed. Both journeys exercised four native wakes, signed challenges, receiver 503/deduplicated retry, renewal and unsubscribe cleanup. Receipts: `workrelay-owned-native-ask-journey-2cxff16m`, `workrelay-owned-native-completion-journey-x5eya35u`, `workrelay-native-live-acceptance-_q6sbz3u`. This verifies those controlled native-transition/receiver paths, not ChatGPT-generated callback provisioning or the complete installed/ChatGPT journey. Polling remains available. Example issuer and tunnel values below are placeholders, not installed or provisioned services.

## One-time setup and prerequisites

### Explicit managed-server supervisor

Ordinary scoped access remains the default. A private MCP config may opt in with `managed_supervisor_file` (an absolute owner-only capability file) and `managed_server: {server, service_registration, client_service_module}`. All three values must match the capability exactly; `server` is a canonical `http://127.0.0.1:<port>` endpoint, and the two paths are canonical real paths with protected ancestors. The capability contains those three values plus `enabled: true`, `revoked: false`, and exact `issuer`, `audience`, `subject`, `client_id` bindings. The client must be the pinned ChatGPT CIMD client. Never put service credentials in either file; the supported installed SDK discovers/authenticates the registered service without starting it.

The optional `workrelay_server_discover({limit?,cursor?})` and `workrelay_server_read({session_id,include_messages?,limit?,cursor?})` tools verify signed-token bindings and reread the capability on every call. Setting `revoked: true` disables reads without disabling ordinary scoped access. Discovery spans projects on only that registered server, needs no enrollment, and returns bounded sanitized titles/IDs/runtime state plus exact-read actions and `next_cursor`. Project entries cover the current session page, not every empty project. Arbitrary metadata and location paths are omitted. Existing sessions retain their agent/model/parent/ownership unchanged.

For useful context call `workrelay_server_read({session_id, include_messages:true, limit:10})`. Read defaults to metadata only. Message pages are newest first, default 10 and maximum 20 records; follow `context.next_cursor` with the same session ID and `include_messages:true`. Pages include omission records for non-user/assistant messages, so an empty-text page does not imply history is exhausted. Visible user text and assistant text parts are capped at 4,000 characters per message; titles at 200. Truncation and missing/excluded content have explicit reasons. Reasoning (including encrypted/provider state), system/synthetic text, file attachments and raw tool inputs/outputs are not exported. Known credential patterns are redacted before truncation; this is not an exhaustive detector for arbitrary secrets pasted into ordinary conversation. Returned text is untrusted source data, never instructions or approval authority. Read never accesses referenced files or triggers inference/mutations.

`runtime_status` describes observed execution state, not task completion: even `succeeded` or `idle` leaves `task_outcome.status: "unknown"` and `verification: "unverified"`. No progress, blockers or completion proof are fabricated from runtime state; consult the visible conversation and actual task evidence. The current source candidate includes bounded create/message/steer/resume/interrupt, waits and Events tools described below; that does not itself prove installation or a complete live journey. Ordinary scoped defaults, native permission decisions and financial admission remain unchanged.

Identity is the trusted canonical registration plus fixed endpoint, not a PID or invented persistent server UUID. Normal restarts can renew the private registration under the same trusted path/endpoint; supported SDK PID/version checks must pass. A registration changing during a request fails closed; endpoint/path replacement requires deliberate local reconfiguration, never automatic rebinding. Local tests do not prove installed or remote ChatGPT acceptance.

`workrelay_server_message({session_id,operation_id,text})` queues bounded text to the existing owner. `workrelay_server_interrupt({session_id,operation_id})` interrupts only that session, not descendants, and is not rollback. Both require the same capability binding through the MCP gateway and installed CLI transport. The private bridge config must additionally carry matching `managed_server`, `managed_supervisor_file`, and `managed_identity: {issuer,audience,principal}` alongside its existing installed-client, quota and pinned guard configuration. No credentials or authorization are supplied by tool arguments. Keep these private references identical to the gateway's binding. No agent/model/parent/intent/permission overrides are accepted. For an existing session, queued inference is admitted only when its **current native model-catalog resolution** is the official OpenAI route and the actual resolved integration is the pinned OpenAI OAuth connection; it need not equal the configured creation-model default or a hardcoded model ID. Credential, quota, guard, identity and resolved integration are rechecked before inference; unsupported/ambiguous routes fail closed, with no API-key or provider fallback. Newly created sessions still use the configured creation-model default. Native permission decisions remain authoritative.

An owner-only `managed-control.sqlite` ledger reserves the operation, deterministic message ID and hashes before POST. Reuse the same operation ID and identical arguments after a lost acknowledgement: exact-message/inbox reconciliation may report `queued_observed`; absence is not permission to replay. A reserved/sending/uncertain operation blocks a different same-session operation until resolved. Only a pre-send reservation whose recorded process is proven absent can be recovered, with fresh financial/authority/identity checks; live/reused/unknown owners remain blocked. Sending/uncertain operations never replay. Queue acknowledgement is not task completion. Interrupt acknowledgement may mean no active execution was interrupted. Revoking the capability blocks reads, controls and managed subscription authorization. These behaviors have isolated local tests, not live managed-server write/Events acceptance.

### Native question recovery and observed delivery

A session can remain native-active while its question tool waits. Queued chat
text is not a form answer: it may remain unread until the question is settled.
Read `workrelay_server_waits` before interpreting a quiet session as stalled.

Use `workrelay_server_question_reply` only for the user's explicit answer to the
exact returned form; use `workrelay_server_question_cancel` only for an explicitly
requested dismissal. Supply the original session/form IDs and a stable operation
ID. A reply's `answer` maps the native field keys to chosen values. These actions
can resume execution and therefore retain financial and model admission. They
never answer native permission prompts or generic authorization/MCP forms.
The form must be corroborated by its originating native question tool call.

Repeated operation IDs must have identical arguments. A lost acknowledgement is
uncertain, not permission to resend; reconcile the existing operation against
native state. A reservation proven unsent and owned by a dead local process can
be reclaimed with the same ID and arguments after all admission checks repeat;
a live or unknown owner, or any sending/uncertain operation, cannot be replayed. Another actor settling a form is not proof that this caller's answer
was delivered. Native state and protected session identity are checked again
before mutation. No automatic answer extraction from conversation text occurs.

`workrelay_server_operation_status` preserves historical receipt-only inspection.
`workrelay_server_reconcile` separately observes native message/inbox and waits,
and atomically persists a verified receipt to clear an unresolved local control.
It makes no native mutation, replay, inference, or task-completion claim. Because
it updates local control bookkeeping, read-only monitors use operation status
and waits instead. Treat `queued_observed`
as queued and `message_observed` as materialized, not as executed or accepted.
Current execution/wait evidence takes precedence over historical idle outcomes;
missing evidence is unknown, never guessed idle. Remote client visibility of
these tools requires a refreshed tool catalog after gateway upgrade.

### Control-ledger upgrade and denial diagnostics

The current source adds nullable `denial_code` and `denied_at_ms` columns to `managed-control.sqlite` through its normal additive migration on ledger open. **Source/tests are not proof that an installed runtime has been upgraded.** Before any migration, coordinate a maintenance boundary: pause new gateway/CLI control requests, allow owned in-flight writers to finish, stop only the owned Workrelay gateway, and verify that **all old and new version ledger writers are stopped**. Do not stop OpenCode, unrelated services or conversations. Take a consistent owner-only private SQLite ledger backup (including required journal/WAL state through a supported backup procedure) and configuration backup before opening the ledger with new code. Older positional `INSERT` statements cannot write the expanded schema; do not run mixed versions against it.

Use one consistent reviewed code version for the gateway and CLI when resuming. For rollback, stop all writers again and restore the compatible pre-upgrade ledger backup with its matching code/configuration; merely downgrading code against the new schema is unsafe. Retain the post-upgrade ledger and operation evidence privately and reconcile effects before resuming—restoring a backup cannot undo a native POST and is not permission to replay missing operations. Preserve existing credential, issuer, grant and revocation state; do not roll those back to revive access. This is an operator procedure, not an instruction to modify private state automatically.

For new pre-POST denials, phase, finite code and observed denial time are committed atomically. The closed `denial_code` set is `QUOTA_DENIED`, `QUOTA_UNAVAILABLE`, `ATTESTATION_FAILED`, `AUTHORITY_UNAVAILABLE_OR_CHANGED`, `SESSION_READ_FAILED`, `MODEL_MISMATCH`, `IDENTITY_CHANGED`, `UNEXPECTED_PREPOST`, `CREATE_CAPACITY_DENIED`, `CREATE_PROJECT_WORKSPACE_MISMATCH`, and `OPERATION_ARGUMENT_CONFLICT`. Codes come from explicit guards or typed errors, never exception-text matching. CLI failures and MCP error/operation-status projections expose these categories; MCP permits `denied_at_ms` only as a nonnegative JS-safe integer, otherwise `null`. Legacy or unknown denial reasons are `DENIAL_REASON_NOT_RECORDED` with null time: no backfill, guessed cause, or fabricated timestamp. Inspect the original operation ID first; diagnostics neither approve a retry nor replay a denied/uncertain operation. Historical unrecorded causes remain unknown.

For an `ATTESTATION_FAILED` denial, `attestation_check_id` is a closed native predicate ID or `null`, projected through both MCP errors and operation-status receipts. IDs identify bounded checks (including metadata-read-unavailable stages), never exception text, paths or source contents. The field is stored atomically with denial phase/code/time; legacy missing detail and malformed/unknown IDs stay `null`, and other denial codes cannot carry a predicate. Non-denied phases omit denial fields. `UNCLASSIFIED` means a new typed failure without a known check, not a reconstructed historical cause. This additive nullable column requires the same coordinated writer pause/backup/upgrade procedure above; source tests do not migrate or certify the installed runtime. Diagnostics do not authorize a retry or pin refresh.

### Everyday managed-server use and Events

#### Read-family inventory

Start with `workrelay_server_capabilities({})` to see the tools actually registered in this gateway and their scoped/managed boundaries. `tools/list` remains the authoritative input-schema catalog. Capability discovery verifies the same pinned principal/client/server binding; it does not grant arbitrary shell or bypass native approvals.

| Power-user stage | Managed-server tools / protocol | What they do and do not do |
|---|---|---|
| Inventory | `workrelay_server_projects`, `workrelay_server_agents`, `workrelay_server_discover` | Bounded, paginated projects/agent definitions/sessions on the one bound server; agents are not running owners. No per-session enrollment is required for the pinned principal. |
| Read | `workrelay_server_read`, `workrelay_server_waits` | Sanitized visible conversation/results and bounded native permission/question waits. Read-only; no inference or permission decisions. |
| Create/select | `workrelay_server_create`, optional `workrelay_server_creation_target` | Create an idle session in a selected native project's verified root; helper only selects the configured default project. Create does not start inference. |
| Control/recovery | `workrelay_server_message`, `workrelay_server_resume`, `workrelay_server_steer`, `workrelay_server_operation_status`, `workrelay_server_reconcile`, `workrelay_server_question_reply`, `workrelay_server_question_cancel`, `workrelay_server_interrupt` | Explicit native question decisions; queue/steer only to the existing owner; recover by operation ID; interrupt only the named session. No owner/model transfer, permission bypass, rollback, or queued-input deletion. |
| Events | `workrelay_event_capabilities`, `workrelay_event_subscriptions`, `workrelay_event_subscription_status`, `workrelay_event_unsubscribe`; protocol `events/list`, `events/subscribe`, `events/unsubscribe` | Bound-server/session lifecycle monitoring. Unsubscribe stops monitoring, not service/work. Receiver and remote client delivery require separate verification. |

Ordinary scoped `workrelay_*` task tools remain available separately. The managed-server family applies only to the exact pinned ChatGPT principal and canonical bound server; it does not widen another principal or server.

- `workrelay_server_projects({limit?,cursor?})` lists known native projects, including projects absent from a session page. IDs are opaque, labels sanitized; paths and workspace commands are not returned.
- `workrelay_server_agents({limit?,cursor?})` lists **definitions at the server default location**, not running owners or every project's configuration. Agent identifiers are opaque navigation IDs, not execution arguments. Names/descriptions are sanitized; prompts, provider requests and permission rules are excluded. Availability does not prove a financially admitted model route or grant execution permission.
- Both inventories default to 20 items, maximum 50. Follow `next_cursor`; if the inventory changes, restart from the first page. Native list responses are bounded to 2 MB / 10,000 records rather than streamed without limit.
- `workrelay_server_discover({search?,limit?,cursor?})` supports native session search (1–200 characters); preserve `search` on subsequent pages. Do not put credentials in search text. Existing session discovery and action arguments remain compatible.
- `workrelay_server_read({session_id,include_messages:true,limit?,cursor?})` provides bounded visible conversation/results. Runtime success is not verified task completion; no authoritative harness progress/blocker/completion report is invented from native metadata.
- `workrelay_server_waits({session_id,limit?})` is read-only (limit 1–50) and returns bounded redacted native permission and question summaries. Permission decisions remain in the native UI; verified question forms may receive an explicit human answer through the exact-form tools below.

The gateway registers ordinary scoped start/status/result/respond/cancel plus these managed controls:

- `workrelay_server_create({operation_id,project_id,title,directory?})`: the pinned server-wide principal may select any discovered native project using its opaque ID. Omit directory to select that project's verified canonical root; MCP forwards omission unchanged, never substituting the profile workspace. An explicit directory must be the selected canonical root or a profile-allowlisted directory within that project. No symlink/traversal or arbitrary filesystem access is granted. Creation is idle, returns a stable session ID and does not start inference. Ordinary scoped defaults remain unchanged.
- `workrelay_server_message`, `workrelay_server_resume`, and `workrelay_server_steer` take `{session_id,operation_id,text}`. Message/resume queue to the existing owner; steer uses native steering. Neither changes agent/model or approves permissions.
- `workrelay_server_operation_status({operation_id,session_id?})` reads a historical durable receipt under the current authenticated principal/server binding without applying today's execution-model guard or observing the native session. Omit session ID when creation never returned one. `CONTROL_OPERATION_NOT_FOUND_CURRENT_BINDING` and `CONTROL_OPERATION_AMBIGUOUS_CURRENT_BINDING` establish only an unresolved lookup **within that binding**, never global absence or proof of no effect: phase is unknown, effect is not established, and replay is forbidden. For not-found, have the operator compare retained original operation/session and binding references; for ambiguity, use the exact original session reference only if already retained, otherwise request operator receipt reconciliation. Do not repeat the same failing lookup, guess a session, change bindings, or replay. A known denied receipt remains distinct from sending/uncertain (`may_have_been_applied`); a current model change does not hide authorized historical receipts or relax write guards. Revoked/wrong-principal/wrong-server access still fails closed. This source behavior is not an installed-fix claim. Interrupt still requires `{session_id,operation_id}` and targets that session only; idle may return `idle_noop`, not rollback or removal of queued work.

`workrelay_server_creation_target({})` is an **optional default-project helper**, not a mandatory enrollment or restriction to one project. It returns the project containing the configured workspace without exposing a private path. Alternatively select a project directly from `workrelay_server_projects`; its create action supplies the opaque ID. In either case omitting directory selects the native project root, which may differ from the configured workspace subdirectory. An unavailable default helper does not remove authority to select another verified native project. The CLI revalidates current project identity, location, model, permissions and financial admission.

For a failed create, inspect the **original operation ID** first. A denied create with `exact_session_exists:false` and `effect:not_applied` is confirmed no effect, not uncertainty. `CONTROL_NOT_SENT` / `no_post_permitted` with `PROJECT_WORKSPACE_MISMATCH` means the selected workspace did not belong to the chosen project (the earlier implementation substituted the profile workspace when directory was omitted). Only allowlisted code/effect/reason fields are surfaced; raw upstream errors are omitted. Never change arguments while reusing that operation ID. After no effect is established and review/live readiness permits, a corrected create uses a selected native project and a **new** operation ID. Unknown or ambiguous recovery is not permission to replay. A prior isolated real idle-create proof covers native-project selection before final retry hardening; it is not relabeled as proof of the final candidate or remote ChatGPT journey.

Reuse identical operation IDs and inputs after uncertainty. All control handoffs use verified caller claims, existing financial admission and native permissions. A native global project rooted at `/` is not a filesystem wildcard: omission is rejected and an explicit profile-authorized workspace is required. Nested project ownership is rechecked. Creation does not authorize arbitrary directories or models. Ordinary scoped defaults remain unchanged.

With Events enabled, callable tools are `workrelay_event_capabilities({})`, `workrelay_event_subscriptions({session_id?,limit?,cursor?})`, and `workrelay_event_subscription_status` / `workrelay_event_unsubscribe` with `{subscription_id,session_id?}`. They share the native Events store and current revocation boundary; status/list omit callback URLs, signing secrets and event text. Creation remains **native `events/subscribe`**, not a nonexistent subscribe tool. Subscription stop removes pending delivery, not underlying work; `revocation_pending` means retry is required, not success. `session.progress` reports explicit observed transitions; the native adapter only emits source-supported states (including explicit idle), not guessed running/retrying state or verified task completion.

### Everyday first call without the managed-server opt-in

Ask “Show me work I can access.” The client should call `workrelay_discover({})` before asking for internal IDs. It lists the single configured permitted workspace, owned Workrelay runs, and explicitly enrolled read-only sessions. Returned actions include the exact `key` or `grant_id` arguments to use next. Pass `next_offset` as `offset` to continue; `limit` defaults to 20, maximum 50. Pages can be empty when stale authority is excluded. Listings are revalidated against current session ownership/project and local enrollment, not a global session search. Concurrent changes can shift offset pages; restart discovery if necessary.

Empty-state guidance explains how to start a new task (choose a new idempotency key and provide text) or request explicit local enrollment of a selected existing session. Discovery neither enrolls/adopts sessions nor starts inference. It reads the ledger without creating it; missing or unavailable sessions are not authority to control them. Agent definitions are templates, not running work, and are not enumerated. The current configuration authorizes one workspace, not every local project. These discovery behaviors have local tests; actual remote-client usability still requires verification after installation.

The current source uses `@modelcontextprotocol/server` 2.3.1 and `@modelcontextprotocol/node` 2.1.1, Streamable HTTP, and Node >=22. Install dependencies with `npm ci`; run `node src/workrelay/mcp.mjs /absolute/path/to/private-mcp.json`. The process listens on loopback only. Keep the existing authenticated OpenCode service on loopback too; **never forward, publish, or disable authentication on OpenCode**. The gateway calls the existing private CLI configuration and does not replace the local OAuth/quota safeguards.

Create a private JSON config owned by the service user with mode `0600` (parent directory private as well). It contains references and non-secret identifiers only; do not put bearer tokens, passwords, private keys, or secret values in it, the repository, prompts, or logs:

```json
{
  "port": 9000,
  "public_origin": "https://your-owned-tunnel.example",
  "issuer": "https://your-established-oauth-issuer.example",
  "jwks_uri": "https://your-established-oauth-issuer.example/jwks",
  "audience": "https://your-owned-tunnel.example/mcp",
  "principal": "immutable-issuer-subject",
  "owner": "configured-local-owner",
  "bridge_config": "/absolute/path/to/existing-private-bridge-config",
  "events_enabled": true,
  "events_state_path": "/private/path/to/events.sqlite",
  "revocation_file": "/private/path/to/principal-revocations.json"
}
```

The three Events/revocation entries are optional for tools-only mode; enable all three for Events. Keep the state and revocation files in a user-owned private, nonsynced directory (mode `0700`), with private files (mode `0600`); do not put them or their backups under Dropbox or any other cloud-sync root. The revocation file is local administrator-controlled data, not an externally supplied credential. The gateway also maintains generation-bound local approval/cleanup markers beside the Events state; protect and back them up consistently with that private state. Do not copy these paths or state into a public deployment.

The example above uses the **external issuer** mode. The exact HTTPS `public_origin` is canonical without a path; `audience` matches `/mcp`. `issuer` and same-origin `jwks_uri` identify a separately operated trusted issuer that issues RS256/ES256 JWTs with immutable `sub`, `exp`, `iat`, audience and `workrelay:tasks` scope. In this mode the gateway validates those claims and advertises OAuth protected-resource metadata but is **not** an authorization server. Configure that issuer/client authorization separately.

Optional self-hosted **local-only source mode** requires private MCP config `issuer_mode: "self-hosted"`, `issuer_exposure: "local-only"`, `issuer_state_dir`, the exact HTTPS `public_origin` and `/mcp` `audience`, plus `principal`, `clientId` and a one-element `redirectUris` list matching the privately provisioned version-1 `issuer.json` (`accountId`, `origin`, client, redirect). The `human.json` account must match as well. Missing, mismatched or permissive state fails before listening. Provision through the private TTY or explicitly generated-file workflow in `docs/issuer-setup-safety.md`; never put keys, passwords or verifier hashes in the MCP config or repository. Keep the issuer state and all backups outside every Dropbox or other cloud-sync root; only the specifically authorized generated password-delivery file may be placed in a private sync directory. The generated-file workflow keeps issuer keys and verifier in private local state, writing only the new password to the separately chosen owner-only delivery file. Local tests use disposable synthetic credentials and a protocol client; they do **not** establish an ordinary browser login over local HTTP or a public HTTPS issuer.

In local-only mode the listener must explicitly bind `127.0.0.1` or `::1`, accepts only that local Host, and rejects supplied forwarding headers. **Loopback is an operator/OS trust boundary, not a proof of non-exposure**: another same-user local process can proxy the port while stripping headers. Do not attach a tunnel, proxy or forwarded public route to this mode.

### OAuth expiry, rotation and reconnect

For the maintained self-hosted OAuth provider, access tokens have a 300-second lifetime. Refresh authorization is supported for up to a fixed 14-day grant lifetime; each successful refresh rotates the refresh token but does not extend that family expiry. Resource access remains bounded to the authorized task scope and existing client, account, redirect, resource and scope bindings.

The reviewed renewal candidate rejects fresh or stale refresh requests with a wrong client/account/resource/scope binding **before** consuming a token or applying replay handling. A concurrent duplicate consume returns OAuth `invalid_grant`, not HTTP 500; refresh-family revocation is atomic. On explicit reauthorization after revocation, the same client/browser may request the already authorized `workrelay:tasks openid` combination and complete fresh consent to create a new authorized grant. This does not restore the revoked grant: its old tokens remain denied. Do not delete/re-add the client registration or treat revocation as permission to silently recreate a grant.

Refresh rotation is strict. If a refresh response is lost after rotation, retrying the old token—or replaying a stale rotated token—returns `invalid_grant` and revokes the affected refresh family. **Transparent retry or a grace window is not implemented.** The supported recovery is an explicit reconnect/authorization flow with the same client and browser context, followed by fresh consent where required; do not automatically replay the old refresh token or remove/re-add the registration as a default fix. This is a documented protocol limitation, not proof of how the ChatGPT UI will behave.

Isolated renewal tests used a 60-second fixture lifetime; live token lifetimes, credentials, scopes and monitoring were not changed. Focused test groups of 15 and 14 passed. The final isolated elapsed gate passed in 223.686 seconds on unchanged source: two real 60-second expiry/refresh/MCP-read cycles, restart persistence, fresh and stale binding preservation, concurrent refresh/replay revocation, lost-response failure behavior, same-client fresh-consent recovery with old tokens denied, and explicit revoke/teardown. An earlier attempt was terminated before completion; that historical failure is superseded by this successful unchanged-source run. The reviewed source candidate based on `20936c6` remains unreleased under the existing immutable `0.1.0` checkpoint. This proves the isolated client gate only—not production deployment, a production-token change, or real ChatGPT reconnect/UI behavior.
